# 小龙虾 U 盘版 · 运行与部署手册

面向自己启动小龙虾客户端和管理后台、做授权配置、打包拷盘的人。命令都在 Windows + Git Bash 下实测过，
文末附实测记录和已发现的坑。

> 授权平台（`oauth.*` 指向的第三方平台，负责登录、套餐、模型目录与算力中转）
> 由你们自己维护和启动，**不在本手册范围内**；手册里只说明客户端需要填哪几个字段。

## 一、先搞清两个角色

| 角色 | 代码位置 | 职责 | 默认地址 |
| --- | --- | --- | --- |
| **客户端** | `E:\github_data\jr_claw`（本仓库） | U 盘上跑的那个 exe：配置向导、网关、聊天通道 | 无（桌面程序） |
| **小龙虾管理后台** | `E:\github_data\xlx-admin-run` | 管授权码、设备记录、版本更新、内置模型下发、事件日志 | `http://127.0.0.1:15000` |

另外还有一个**外部依赖**：授权平台（`oauth.issuer` 指向的地址），提供 OAuth 登录、套餐订阅、
模型目录，客户端通过 `app.config.json` 的 `oauth` 段对接，本手册不涉及它的部署。

数据流：

```
客户端 ──① 本地授权：data/license.json 绑定 U 盘卷序列号（离线）
       ──② 后台联检：POST 管理后台 /api/client/license/check（授权码 + U 盘ID）
       ──③ 登录/套餐/模型：OAuth 授权平台（外部平台，自行维护）
       ──④ 更新：管理后台 /api/client/update/check，下载新 exe 自动替换
```

①②④ 都由本手册覆盖；③ 是完全可选的：只配手动模型（自定义 baseUrl + Key）时不需要授权平台，
不联网的单机交付也可以把 `backend.url` 留空，客户端会自动跳过 ②④。

## 五、客户端如何指向管理后台与授权平台

配置优先级：**U 盘根目录 / exe 同级的 `app.config.json`** 覆盖 **包内 `resources/app.config.json`**
（深合并，只写要改的字段即可），改配置不需要重新打包。

```jsonc
{
  "backend": {
    "url": "http://127.0.0.1:15000",   // 管理后台地址；留空则跳过授权联检/更新/模型下发
    "licenseKey": "XLX-DEMO-0001",     // 后台创建的授权码
    "channel": "stable",               // 与后台授权码的 channel 一致
    "reportOnly": true                 // true=只上报不拦截（联调期建议保持）
  },
  "oauth": {
    "issuer": "http://127.0.0.1:8080",            // 授权平台地址（外部平台，你那边起）
    "authorizationOrigin": "http://127.0.0.1:8080",
    "clientId": "jr_client_5730df3e-901",
    "clientSecret": "jr_secret_...",
    "redirectUri": "http://127.0.0.1:18790/api/auth/callback"
  },
  "ports": { "gateway": 18789, "oauthCallback": 18790 }
}
```

开发目录里已经有这样一份 `app.config.json`（gitignore，不随包分发），
指向本机 `127.0.0.1:15000`；交付包里 `resources/app.config.json` 指向线上地址
（后台 `111.6.204.34:6005`、授权平台 `192.168.0.73:8080`）——**交付前记得把后台地址换成真实地址**
（授权平台地址你那边按实际改），否则客户的 U 盘到手里连不上。

## 七、授权机制全解（两层，别混）

### 第一层：本地授权文件（离线，管"这个 U 盘能不能跑"）

```bash
zgyclaw-windows-amd64.exe --bind-usb       # 为当前 U 盘生成 data/license.json
zgyclaw-windows-amd64.exe --check-license  # 校验当前授权
```

- 授权文件绑定 **U 盘卷序列号指纹**：指纹 = `SHA-256(产品盐 + 平台 + 卷序列号)`，
  卷序列号读不到时回落到磁盘序列号；授权文件本身是 `XLX-LICENSE-v1:` + base64（内含签名），
  手改会被签名校验拒绝（`BAD_LICENSE_SIGNATURE`），换 U 盘则报 `DEVICE_MISMATCH`；
- 拷到别的 U 盘直接不通过，复制文件也没用（指纹不同）；
- 文件统一放在 exe 同级的 `data/license.json`（旧版根目录的 `license.dat` 已废弃并在启动时自动迁移）；
- 母本 U 盘与客户 U 盘用同一条命令，没有区别；
- 开发模式（未打包）跳过校验。

### 第二层：后台授权码（联网，管"账号是否有效、要不要更新、下发什么模型"）

- 客户端启动时带 `licenseKey` + `usbId`（U 盘指纹）请求 `/api/client/license/check`；
- **首次校验自动把该 U 盘序列号写进这条授权**，之后换 U 盘会返回 `USB_MISMATCH 授权与当前U盘不匹配`；
  要换机器/换盘，在后台把这条授权的 U 盘 ID 清空（页面上有"清空 U 盘 ID"按钮）或改成新 ID 即可；
- `reportOnly: true` 时校验失败只记录不拦截，适合联调；正式发行可改 false 变成硬拦截；
- 授权码的 `channel` 与 `modelGroup` 决定它能拿到哪个版本、哪组模型。

> 两条线是叠加的：本地文件授权保证"盘被复制也跑不起来"，后台授权码保证"运营可控可统计"。
> 客户完全不联网时，第一层仍能独立工作。

```
U 盘根目录
├── zgyclaw-windows-amd64.exe      # 唯一程序文件
├── app.config.json      # 可选：覆盖包内默认配置（改后台/OAuth 地址靠它）

    ├── .openclaw/       # openclaw 配置与运行期文件
    ├── npm/             # 按需安装的插件（如 QQ 插件）
```

拷盘步骤：

1. exe 拷到 U 盘根目录；需要改地址就把 `app.config.json` 一起放过去；
2. 拔插到目标机器，双击 exe（首次启动会自解压到临时目录，属正常）；

注意：`data/` 是**跟着盘走**的运行期目录，别把开发机的 `data/` 拷给客户——
里面有你自己的登录态、凭证和 sqlite 会话，客户启动会直接继承（也容易泄漏）。

## 十、更新流程

1. 后台"版本管理"新建版本：填版本号、平台 `windows`、架构 `x64`、通道 `stable`、
   下载地址（exe 的可直链 URL）、`sha256`、更新说明，勾选"发布"；
2. 客户端检查更新 → `needUpdate: true` 时下载到 `data/update/downloads/`，
   校验 sha256 一致后写替换脚本、退出主进程、由脚本覆盖 exe 并重启；
3. 校验不一致直接删包并报错，不会替换。

调试期可以先用后台演示版本（`2026.7.24`）练手，客户端版本号取自包内 `product.version`（当前 `3.0.0`）。

## 十一、后台心跳与登录令牌保活

这两件事都由 `src/main/services/keepalive.js` 在启动链末尾开启、退出时停止。

**后台心跳**：客户端启动后立刻打一次 `/api/client/device/ping`，之后每 5 分钟一次，
带上 `licenseKey` / `usbId` / `machineId` / 主机名 / 系统 / 架构 / **U 盘文件系统** / 客户端版本。
后台"设备记录"里的"最近在线时间"因此是活的；此前只在启动时校验一次授权，设备时间会停在启动时刻。
心跳失败只写日志，下个周期重试，不影响任何本地功能。

**订阅令牌保活**：授权平台给的 `access_token` 默认 2 小时有效，而它同时是网关调用算力的
Bearer 令牌（客户端把它写进 provider 的 `apiKey`）。所以：

- 令牌距过期不足 15 分钟时自动用 `refresh_token` 换新（`refresh_token` 是一次性轮转，换来的新值会存回会话文件）；
- 换到新令牌后**立刻回写 provider 的 `apiKey`**；网关正在跑就重启一次让它读到新令牌
  （网关启动时才读配置文件，不重启就仍在用旧令牌）；
- 手动填自己 Key 的安装（provider 没有 `keyMode: "server"`）完全不参与这套逻辑；
- **只有 `refresh_token` 也失效**（平台返回 `invalid_grant`，例如超过 30 天或触发重用检测）
  才判定登录失效：清掉本地会话并让界面回到登录页；网络抖动等失败保留登录态，下个周期自动重试。

> 平台侧的重用检测很敏感：同一个 `refresh_token` 被用两次会吊销该用户在本应用下的全部令牌。
> 客户端因此对刷新做了单飞（同一时刻只有一个刷新在跑）并强制持久化轮转后的新值。

## 十二、模型下发怎么用

后台"模型管理"里配置的 provider 会作为**内置模型**下发，客户端合并进 `openclaw.json`
（不覆盖用户在客户端自己填的 provider 字段，只在后台 `forceDefault` 时改默认模型）。

客户端的**出厂模板不带任何 provider 与默认模型**：本地 provider 只可能来自三处 ——
订阅登录同步（`zgy`）、后台下发（带 `source: "backend"` 标记，后台不再下发时会被回收）、
向导里手填的 provider。模板里预置一个会出现"后台已停用、客户端还在显示"的幽灵模型，所以不放。

一条模型要真正下发成功，必须同时满足：

- `enabled = true`；
- `channel` 与该授权码的 `channel` 一致（默认 `stable`）；
- `modelGroup` 与该授权码的 `modelGroup` 一致（默认 `default`）；
- `modelsJson` 是**非空**的 JSON 数组（空数组会被跳过）。

### 模型展示名带品牌前缀（让人看清归属）

网关那套聊天界面（127.0.0.1:18789）的模型列表**只显示 `models[].name`**，
只有两个模型显示名完全相同时才会补一个 provider id 后缀（如 `· zgy`），
provider 的 `displayName` 根本不参与拼装。所以客户端在写配置时统一给模型名加品牌前缀：

- 有 `displayName` 的 provider（订阅同步的 `zgy`、后台下发的）→ `中广云 · DeepSeek V4 Flash`；
- 没有 `displayName` 的（向导里手填的）→ 原样保留；
- 已带同前缀的不重复加。

前缀在写入路径的字段归一化里做（`normalizePortableFields`），任何一次写配置都会补齐，
启动时也会回写一次，所以升级前写好的旧配置在首次启动后就带上前缀。
`name` 纯展示字段，实际调用走 `providerId/modelId`，改它不影响请求。

`keyMode` 决定 Key 来源：`client` 表示用客户自己在向导里填的 Key（下发配置里 `requiresClientKey: true`），
`server` 表示下发平台自己的 Key（后台加密存储，下发时解密）。

## 十三、微信通道的绑定语义（单账号）

一个 U 盘同一时间只服务一个微信号，绑定关系落在 `data/.openclaw/openclaw-weixin/`：

- `accounts.json` 是**启用集合**（插件 `listWeixinAccountIds` 直接读它），列到的账号都会被网关加载；
- `accounts/<accountId>.json` 存凭据（token、savedAt、baseUrl、微信 userId）。

因此：

- "重新绑定"是**替换**：新号绑定成功后，客户端把旧号从索引移除并删掉它的凭据、同步缓存、
  上下文令牌与授权名单（旧号不会继续收消息）；点击按钮时不动数据，避免点了不扫把可用绑定弄没；
- 同一个微信号重扫时插件自身会去重，不需要客户端插手；
- 已绑定状态由这些落盘文件推导，所以切页签、重启应用都不会退回"请重新扫码"；
- 想换号就在面板点"重新绑定"，扫码即可；不需要（也不支持）在多个历史绑定之间切换。

### 二维码过期了会自己换吗

会，微信和 QQ 走的是同一套实现（`src/main/services/qr-session.js`），参数在 `timing.qrSession`：

- 二维码失效后，客户端会在**冷却 15 秒**后自动重新生成（重新拉起登录子进程 / 重新调 QQ 连接器）；
- 连续自动重建最多 **3 次**，且面板在换码期间保持轮询、新码出现自动重绘，用户接着扫最新的码即可；
- 超过上限才停下并提示"已停止自动生成，请点击刷新二维码"，这时需要手动点一下（人工点击会重置额度）；
- "重新绑定"是人工发起，同样会重置额度；已绑定成功后状态不再回退。

各通道只负责"怎么发起一次尝试、怎么结束当前尝试"，状态、二维码缓存、冷却与次数上限、等待与通知都在会话里，
所以微信与 QQ 的换码行为一致，后面再来扫码类平台直接复用同一套。

## 十五、首次运行为什么慢（冷启动与加载页）

现象：全新解压（或换一台电脑第一次插盘）后，第一次点微信「扫码连接」要等一分钟左右才出二维码。

原因既不在网络也不在二维码本身，而是 **openclaw 组件在本机的第一次启动**：模块压缩包刚解压出来的
那棵 `node_modules` 第一次被执行时，要付 Windows 首次读取扫描 + 冷文件缓存的代价（约为热启动的十倍）。
本机实测：

| 场景 | 到出码耗时 |
| --- | --- |
| 刚解压出来的模块树，第一次启动 | 54.8 秒（其中光等到第一行输出就 28 秒） |
| 同一棵树，第二次启动 | 4.7 秒 |
| 二维码本身（微信 ilink 接口取码） | 约 0.3 秒 |

排查锚点：`data/.openclaw/state/openclaw.sqlite` 的创建时间就是 CLI 完成引导的时刻；
`data/.openclaw/logs/wechat-login.log` 的 `qr ready in Xms` 是拿到二维码的耗时；
插件自身日志在 `%TEMP%\openclaw\openclaw-<日期>.log`（毫秒时间戳，能看到 `QR code received`）。

界面上的处理：

- **启动加载页把首次冷启动挡掉**：启动链紧接着拉起一次微信登录子进程（`prewarmWechatLogin({ warmup: true })`），
  渲染层的加载页会等它出码再进向导（`channels.wechat.warmup` → `warmupWechatRuntime()`，上限
  `timing.boot.warmupTimeoutMs`，默认 120 秒）。首次启动的加载页文案会变成
  "首次运行需要准备组件，请稍候…"，之后进向导 BOT 页直接有二维码，不再等。
  已热过（有 `.zgy-warm` 标记）或已绑定微信号时这一步立即返回，不额外拉起进程也不加长启动；
  `warmup` 只跳过"通道是否已启用"的检查；
- 会等十几秒以上的操作统一盖加载页（`src/renderer/src/components/LoadingScreen.jsx`，与启动引导同一套画面），
  面板上那份（按 `.zgy-warm` 标记判断）是兜底：比如缓存被清掉后在运行中重新扫码，仍然会被解释清楚；
- 判断"是不是首次"不靠猜时间：组件第一次成功出码后，会在模块缓存目录落一个 `.zgy-warm` 标记
  （`<本机缓存>/ZgyClaw/cache/<产品目录哈希>/node_modules/.zgy-warm`），之后启动不再提示；
  模块重新解压时该标记随 `node_modules` 一起消失，冷启动代价与提示同步恢复；
- 模块缓存与标记都在本机、不在 U 盘上，因此换一台电脑第一次插盘会再经历一次冷启动。

## 十六、配置写入来源日志（排查用）

每次写 `openclaw.json` 都会在 `data/.openclaw/logs/config-writes.log` 追加一行，用来回答
"这次配置是谁改的、provider 和 Key 变成了什么样"：

```
via E:\github_data\jr_claw\src\main\services\process-manager.js:306 providers=[zgy(server,key=70)] => [zgy(server,key=70)]
```

- `via` 是调用点（文件:行），可据此定位是启动链、向导保存、令牌保活还是后台模型同步写的；
- `providers=[...]` 是本次入参与合并结果的概览：`id(keyMode,key=长度)`，
  `key=enc` 表示还是加密包络、`key=0` 表示没有 Key；
- 出现 `key-preserved=[zgy]` 说明这次写入想抹掉订阅 Key，被护栏用磁盘上的旧值拦下了；
- 出现 `provider-dropped=[...]` 说明合并时该 provider 被入参的 provider 集合排除掉了。

### 已知问题：后台的部分更新会清字段（仅影响直接调 API，页面操作不受影响）

`ModelConfigServiceImpl.save()` 与 `VersionServiceImpl.save()` 用"请求没带就用默认值"的写法：

```java
item.setModelsJson(blankTo(req.modelsJson(), "[]"));        // 不带 modelsJson → 模型列表被清空
item.setDefaultModel(req.defaultModel());                   // 不带 → 默认模型被清空
item.setEnabled(req.enabled() == null || req.enabled());     // 不带 → 静默变成启用
item.setForceUpdate(Boolean.TRUE.equals(req.forceUpdate())); // 不带 → 强制更新被关掉
```

后果：像 `PATCH /api/admin/models/1 {"enabled":true}` 这种只带一个字段的调用，
会把该模型的 `modelsJson` 覆盖成 `[]`，从而下发不到客户端。
后台页面（`/admin/index.html`）保存时总是提交整条记录，所以页面操作是安全的；
用脚本/接口做局部修改时要带齐字段。若要根治，把这些行改成"缺省时保留原值"
（例如 `blankTo(req.modelsJson(), item.getModelsJson())`、`req.enabled() == null ? item.getEnabled() : req.enabled()`）。

## 二十一、各通道凭据从哪来（官方入口）

面板上要填的凭据都来自各平台自己的后台，客户端只是把值存进 `openclaw.json`：

| 通道 | 面板要填 | 去哪拿 | 面板链接指向 |
| --- | --- | --- | --- |
| 微信 Clawbot | 不用填，扫码授权 | 手机微信扫面板二维码 | 无（扫码即完成） |
| 企业微信 | Bot ID、Secret | 企业微信管理后台 → 智能机器人 → 新建机器人 → 手动创建 → API 模式 → 长连接，保存后页面直接给出 Bot ID 与 Secret | `open.work.weixin.qq.com/help2/pc/21677`（官方 How to access Bot ID and Secret） |
| 飞书 / Lark | App ID、App Secret | 飞书开放平台开发者后台 → 选中应用 → 凭证与基础信息（App ID 与 App Secret 同页） | `open.feishu.cn/document/faq/trouble-shooting/how-to-obtain-app-id` |
| 钉钉对话 | Client ID（AppKey）、Client Secret（AppSecret）、Robot Code | 钉钉开放平台 → 应用创建与配置（企业内部应用，开启机器人能力并选 Stream 模式） | `open.dingtalk.com/document/dingstart/create-application` |
| QQ 机器人 | 不用填，扫码绑定 | QQ 机器人开放平台创建/选择机器人后扫码 | 无（扫码即完成） |

链接地址集中在 `resources/app.config.json` 的 `channels.docs`（键是通道 id：`wecom` / `feishu` /
`dingtalk-channel`），U 盘根目录放同名 `app.config.json` 即可覆盖，不用重新打包；
某个通道留空或删掉，面板里就不再出现那条链接。微信与 QQ 是扫码绑定，不需要文档链接
（BOT 页底部原来那条"接入文档"与面板内链接指向同一个地址，已去掉）。

### 通道插件从哪加载（改插件时先看这张表）

客户端会**自动给已启用的通道插件登记加载路径**，每个通道只登记一条，避免同一插件被两个路径重复加载
（openclaw 会报 `duplicate plugin id`）。优先级：随包目录 `resources/plugins/<插件名>` → 模块缓存里的同名包。

| 通道 | 插件来源 | 说明 |
| --- | --- | --- |
| 微信 | `resources/plugins/openclaw-weixin` | 自包含，登录子进程也用它 |
| 企业微信 | `data/.openclaw/extensions/wecom-openclaw-plugin` | 走 `resources/payload/wecom-plugin-extensions.zip` 按需解压（**openclaw 官方安装布局**，extensions 目录自动发现、不登记加载路径）。包里不含 `node_modules/openclaw` 链接（指向本机模块缓存、随机器变化），`installWecomPlugin()` 激活时自动重建。官方 2026.5.7 时期手工目录+加载路径的分发方式与 openclaw 2026.6.1 的多轮注册不兼容（`WeCom runtime not initialized`），已弃用 |
| 钉钉对话 | `resources/plugins/openclaw-dingtalk-channel` | 模块包里没有，只能随包分发 |
| 飞书 | 模块缓存 `<本机缓存>/…/node_modules/@openclaw/feishu` | 随模块包分发（带 `@larksuiteoapi/node-sdk` 等依赖），resources 里不再放一份 |
| QQ | `data/npm/projects/openclaw-qqbot-…` | 模块包里没有，走 `resources/payload/qqbot-node_modules.zip` 按需解压 |

模块包里没有的通道插件，走**按需 payload 机制**（`src/main/services/modules.js` 的 `PAYLOADS` 登记表 +
`ensurePayload()`）：压缩包放 `resources/payload/`，首次用到时解压到目标目录并校验清单文件，
已就位就直接返回。新增平台只需加一条登记（压缩包名、目标目录、清单文件），不用再写解压逻辑；
压缩包格式不限，`tar` / `tar.gz` / `zip` 都由系统 tar 解。

注意：模块缓存是合法的插件目录（`reconcilePluginLoadPaths` 白名单里有它）。重建
`resources/payload/openclaw-modules.tar.gz` 时不要用 `--omit=optional`，否则飞书插件及其依赖会丢；
企业微信已改走独立的 payload（官方安装布局），模块包里不再包含 `@wecom/*`（已作为无用副本移除，
反向依赖核验过：openclaw 本体与飞书/微信插件都不引用它）。

注意：打开文档需要联网，客户端本身离线也能正常跑（扫码绑定等流程都走各平台自己的通道）。

## 二十二、"聊天工具"按已配置展示与向导保存修复（2026-09-14 晚）

实测反馈（微信已扫、飞书已填、QQ 已扫，确认页只显示两个；选了没配的企业微信/钉钉也会出现）
暴露出两个问题：

1. **清单来源错了**：确认页原来按"插件启用位 + 当前选中通道"拼清单，而向导里的 `config`
   是进向导那一刻的快照——BOT 页扫码/保存的配置由主进程随时落盘，快照看不到，
   于是只显示出"选中项 + 旧启用项"，选了没配的通道也会被临时算成启用。
2. **旧快照回写**：`保存并启动` 直接把进向导时的快照写回 `openclaw.json`，
   会把 BOT 页里刚写入的通道凭据/启用项覆盖掉（第一轮保存后磁盘上只剩一个通道就是这个原因）。

改法与验证口径：

- 确认页、运行页的"聊天工具"一律取 `channel:summary`（`channelSummary()`）：
  **扫码绑上或凭据填全才算已配置**，向导里仅选中没配置的不展示；清单进页实时读，不再拼快照。
- 飞书按所选域名显示：选"飞书（国内）"显示 `飞书`，选"Lark（国际）"显示 `Lark`
  （`channelSummary()` 的 feishu 项带 `domain`，渲染层 `channelDisplayName` 取名）。
- `保存并启动` 保存前重新 `config:load` 读最新值再改，不再回写旧快照；
  通道插件在扫码/保存成功时已各自启用（微信扫码、QQ 扫码、三家的保存接口都会写启用位），
  "按当前选中启用通道"这一步删除——没配置的通道不因选中过而被启用。
- QQ 面板进面板自动装插件并直接生成绑定二维码（与微信面板一致），按钮保留用于重新生成/重新绑定。
- 加载页进度条改为匀速横穿、起止两端都完全在轨道外（`loading-slide` 关键帧改 `-100% → 200%`、
  动画用 `linear`），循环重新开始时不再有跳变。

### 飞书私聊策略（配对审批）怎么用

飞书面板里"私聊策略"决定**陌生人私聊机器人时要不要审批**，配置保存后随时可切：

- **需要配对审批**（默认）：陌生人第一次私聊机器人，机器人会回一个**配对码**；
  对方把码告诉你，你回到飞书面板，在"私聊策略"下方的待审批列表里点"批准"，之后对方就能正常对话。
  列表默认空着，"刷新列表"可手动拉一次（有人扫码后会自动出现）。
  **已批准的用户**列在待审批下方（显示审批时记下的名字 + 用户 ID），随时可点"取消批准"收回权限；
  名单同时在配置里时，收回需重启网关生效（界面会出现"重启生效"按钮）。
- **开放（人人可私聊）**：企业内任何人私聊机器人都能直接对话，不需要配对码。
  切换立即生效（主进程写配置并重启网关）。

日常使用不动它就行：默认的"需要配对审批"最稳妥，只有想让全企业随手可用时才切"开放"。

切换只写配置（立即返回，不等重启），网关重启后生效——工作区底部或运行页会出现
「重启生效」按钮，攒着和其它通道的修改一起一次应用。

### 启动之后去哪操作通道（通道设置）

配对请求只在网关运行、机器人在线时产生，而向导只走一次——所以运行页右下角有**「通道设置」**按钮，
点开是整窗的通道面板工作区（与向导 BOT 页同一套 `ChannelWorkbench`，图标栏 + 各通道面板），
网关不用停就能操作：

- 飞书：批准配对码、切私聊策略、改凭据；
- 微信 / QQ：重新扫码绑定；
- 企业微信 / 钉钉：改凭据。

**保存/扫码绑定只写配置，不逐次重启网关**：改 5 个平台不用等 5 次十几秒的重启——
每次保存或绑定成功只是登记"待重启"标记，工作区底部（和运行页）会出现
**「重启生效」**按钮，都改完后点一次统一应用；网关没在跑时不显示按钮，
下次启动自然加载最新配置。标记在网关真正启动时清空。

### 「恢复出厂设置」是什么（原"重新配置"按钮）

原按钮叫"重新配置"、弹窗承诺"保留通道凭证"，但实际调的 `resetAll()` 是**出厂重置**——
文案骗人、会丢数据，已改名「恢复出厂设置」并如实写明清空范围：

- 清空：模型配置、通道绑定与凭据（微信/QQ 扫码、飞书/企微/钉钉凭据）、聊天数据、日志；
- 保留：U 盘授权（`license.json`）、插件缓存（`npm`、`extensions`）；
- 重置前主进程会先停 QQ 扫码会话并 `shutdownAll()`（网关、微信登录子进程、钉钉桥），
  同时清掉微信扫码会话的内存态（主进程不随重置重启，不清会继续显示旧的"已绑定"）；
- 删除 data 时对被占用的路径**带重试**（Windows 句柄释放有延迟），仍有删不掉的会**如实报错**给界面
  让用户重试，不再静默留下"配置已清、绑定文件还在"的半清状态。

正式发布包里没有开发用的 `scripts/reset-data.bat`，用户从零开始就走这个按钮；
开发本机想快速清数据仍可用 bat（两者清理范围一致，bat 不经过界面）。
